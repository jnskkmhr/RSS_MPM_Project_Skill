## Goal
A numerical benchmark of streaming MPM, with and without adaptive particle activation (sleeping), against full-domain MPM. Three questions:
1. Does it scale with terrain size?
2. Does it scale with the number of environments?
3. Does it preserve terrain history?

Sleeping is presented together with streaming as part of the method, not as a separate contribution.

## Terms
The unified code's names are used here. The paper and older outputs use the names on the right.

| Here | Paper and older outputs |

| stream without cache (fixed pool) | recycling, `recycle_nocache` |

## Setup
- **Body.** The box probe for every number: a 0.2 x 0.2 x 0.1 m, 10 kg rigid box on a PD-driven gantry, no robot and no policy, so every mode sees the same prescribed motion. G1 is used only for the lemniscate in step 4.
- **Modes.** Six, differing only in how the terrain is managed. Material, voxel size, sand depth, and timestep are identical.

  | Sleep | Terrain |
  |---|---|
  | off | full |
  | on | full |
  | off | stream without cache |
  | on | stream without cache |
  | off | stream with cache |
  | on | stream with cache |

- **Patch.** 1.2 x 1.2 m simulated, with a 0.2 m boundary on each side (1.6 x 1.6 m in total). This is the streaming preset's default, the training setting, and the size the earlier box runs used.

## Steps
1. **Port the box probe** to the unified code, without changing shared code. Record the commit.
2. **Scale with terrain size.** One environment. The terrain is a corridor: `length_y` equals the patch's total width, and `length_x` grows from the patch length upward. `full` simulates the whole corridor; the streaming modes drag the box the same distance along it. The box is pushed along x.
3. **Scale with the number of environments.** The terrain per environment is fixed at the size used for locomotion training. Sweep `num_envs` on one GPU for all six modes, up to the largest count that fits, and record how the next count fails.
4. **Preserve terrain history.** Compare `full`, stream without cache, and stream with cache, one run each:
   - **Box** dragged along a lemniscate (figure-eight) for at least two laps. The lobes are larger than the patch, so the earlier track leaves the patch and re-enters it.
   - **G1** walking the same kind of lemniscate, with a PD controller on `vx` and `wz` that tracks the path, so the robot returns to its own footprints. Height maps and video only: the robot's motion differs between modes, so its forces are not compared.
   - **One-time check:** run `full` twice with identical settings. If the two force traces overlap, one run per mode is enough. If they do not, show both.
5. **Debug check, not a paper result.** On fresh terrain (an indentation and a straight drag), compare the streaming modes against `full`. Record the outcome under caveats, with no slide.

## Acceptance criteria

| # | Question | Metrics | How it is measured |
|---|---|---|---|
| P1 | Does it scale with terrain size? | Peak VRAM, physics time per step, step time (mean, 95th percentile), GPU utilization (mean, max), each against `length_x`, six modes | Step 2 |
| P2 | Does it scale with the number of environments? | VRAM per env, time per step per env, GPU utilization, largest env count that fits, and the failure at the next count, six modes, at the training terrain size | Step 3 |
| P3 | Does it preserve terrain history? | On revisited track, for stream with cache against `full` and for stream without cache against `full`: terrain height difference and force profile (Fx, Fy, Fz) for the box; terrain height for G1 | Step 4 |
| P2b | Does streaming MPM train a policy faster? (added 2026-11-22, reported with P2) | Success rate against wall-clock time and against environment samples, streaming with cache against MPM full, same GPUs, same starting policy, same number of environments per GPU. State how success rate is defined, the number of seeds, and every difference between the two tasks besides terrain management | G1 PPO training runs; section "Training-speed benchmark" of `outputs/T1.md` |

Measurement rules, which apply to every row:
1. **Timing** includes host-side tile paging and synchronization; excludes rendering and warm-up. State the warm-up length.
2. **GPU utilization** is the `utilization.gpu` value from `nvidia-smi` (percentage of time the GPU was executing a kernel), sampled at a fixed stated interval over the same timed window as the step time. No other job runs on the GPU during the measurement. Report it next to step time, not instead of it: low utilization with a long step time means the step is waiting on the host, not on the GPU.
3. **Peak VRAM** states whether it is the process peak (including the CUDA context) or the allocator peak.
4. **Axes.** P1 plots against `length_x`. Particle counts are not an axis, because the streaming modes do not grow; give full's particle count in the caption.
5. **Like for like.** `full`'s corridor is as wide as the patch's total width. Any setting that differs between modes besides terrain management is listed.
6. **Conditions** for every result: box dimensions and mass, trajectory, material, voxel size, sand depth, patch size, GPU, commit, and number of runs.

## Out of scope
- The policy-level effect of the cache: it needs training.
- Patch-size, boundary-width, and discretization ablations. Resolution belongs to T4.
- Strain and region activation as separate rows. They are reported as one mechanism, "sleep".
- Run-to-run reproducibility of the simulator as a question of its own. The one-time check in step 4 only decides whether one run per mode is enough.
